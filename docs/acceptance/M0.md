# M0 acceptance criteria: audit of the Phase 1 storage engine

This file, the runner and the patches were committed before any test,
harness or experiment below was run. `results/audit/m0/env.txt` records the
commit each run came from. Everything runs from `scripts/audit/m0/run.sh`, one
step at a time, so disk-heavy steps never overlap.

`go build`, `go vet` and `gofmt` were run once before the initial commit to
confirm the code compiled. They are run again here as A1 and A2, and only
these runs are reported.

## A. Test suite on the unmodified code

| ID | Command | Pass criterion |
|---|---|---|
| A1 | `gofmt -l cmd internal` | prints nothing |
| A2 | `go vet ./...` | exit 0 |
| A3 | `go test -count=1 ./...` | exit 0 |
| A4 | `go test -race -count=1 ./...` | exit 0 |
| A5 | `go test -race -count=5 ./...` | exit 0 (flake check) |
| A6 | `go test -cover -count=1 ./...` | exit 0; coverage is reported, no threshold is set |

Test seeds are fixed in the test source.

## B. Crash harness on the unmodified code

| ID | Command | Seed | Pass criterion |
|---|---|---|---|
| B1 | `crashtest -trials 500 -seed 1` | 1, the seed of `results/crash.json` | `passed == 500`, `failed == 0` |
| B2 | `crashtest -trials 500 -seed 20261101` | 20261101, a seed never run before | `passed == 500`, `failed == 0` |

The seed fixes the kill delays and the operation stream. It does not fix how
far the child gets before each kill, because that depends on the OS scheduler,
so `total_acked_ops` will differ from the 151,604 in `results/crash.json`
even with seed 1. Matching that number is not a criterion. `results/crash.json`
itself is left untouched; these runs write to `results/audit/m0/`.

## C. Published numbers match their source

| ID | Check | Pass criterion |
|---|---|---|
| C1 | run `cmd/results` on a copy of the commit | `README.md` and `results/RESULTS.md` are byte-identical afterwards |

`cmd/storagebench` is not rerun in M0: the task is the test suite and the
crash harness.

## D. Experiments on patched copies

These test what the harness and the docs actually prove. They run on throwaway
copies built with `git archive`, and the patches are in `scripts/audit/m0/`.
The repository's code is not changed. All harness runs use seed 1 and 100
trials. A prediction is not a pass criterion: each result is reported whichever
way it falls.

| ID | Patch | Question | Prediction |
|---|---|---|---|
| D1 | `no-fsync` | Does the harness notice if the WAL never calls fsync? | Passes 100/100: SIGKILL leaves the page cache intact, so the harness cannot see a missing fsync |
| D2 | `ack-before-durable` | Does the harness notice if a write is acknowledged before it reaches the WAL file? | Fails: this is the bug the harness is built to catch |
| D3 | `harness-probes` | How much WAL does each child have to recover at start-up? | 0 bytes in all 100 trials: the parent recovers and cleanly closes the directory first, so no kill lands during a real recovery |
| D4 | `harness-probes` | How often does `cmd.Wait` close the ack pipe before the reader reaches EOF? | No prediction: reported as a count |
| D5a | `engine-probes` | Can `Get` lose a key if a flush installs between its snapshot and its version capture? | Fails: `ErrNotFound` for a key that always existed |
| D5b | `engine-probes` | Does D5a happen with no injected pause, in a 60 s stress run with `GOMAXPROCS=2`? | No prediction: the stale and not-found read counts are reported |
| D6 | `engine-probes` | Does calling `Next` on an exhausted iterator stay safe? | Fails: index-out-of-range panic |
| D7 | `engine-probes` | Is a value over the WAL's 64 MiB replay limit rejected up front? | Fails: `Put` succeeds, the key is gone after reopen |
| D8 | `engine-probes` | Does the bloom filter use the k = 7 the docs state? | Fails: `int(10 * 0.69)` is 6 |
| D9 | `engine-probes` | Is a bit flip in the middle of the newest WAL segment reported? | Fails: `Open` succeeds with 0 of 100 acknowledged keys |

The D5 to D9 tests assert the correct behaviour, so a failing test confirms a
bug and a passing test clears the suspicion.
