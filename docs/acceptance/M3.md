# M3 acceptance criteria: replicated KV

Committed before any M3 code was written or run. The planted-bug patches and the
runner come after the code they apply to, and are committed before they run.
`results/audit/m3/env.txt` records the commit of each run.

## Scope

- **Replicated KV.** `internal/kv` applies committed Raft entries to the LSM engine.
- **Exactly-once writes.** Each client has a session, and each write a request ID.
  A retried write applies once. The session table lives in the engine and is
  updated atomically with the write, which needs an atomic batch in the engine.
- **Linearizable reads.** Reads use ReadIndex. A test shows a plain leader read
  returning stale data, and `LEARNING.md` explains why.
- **Snapshots.** Raft can discard its log through a point the state machine has made
  durable, and the on-disk log shrinks with it. A follower too far behind receives
  the state through InstallSnapshot.

Out of scope, for M4 and later: a real network, a client library for real use,
session expiry, and splitting a snapshot into chunks.

## S. Simulation

Every schedule now runs the whole stack: clients, sessions, ReadIndex, snapshots and
the state machine, all on the M2 fault model. All M2 checks stay on. These are added:

| Check | Meaning |
|---|---|
| `kv-exactly-once` | no acknowledged or retried write appears twice in any read |
| `kv-linearizable` | a read sees every write acknowledged before it started, every value a completed read already saw, and agrees with all other reads |
| `kv-lost-write` | after the faults stop, every acknowledged write is in the final read |
| `kv-phantom` | a read never returns data no client wrote |
| `kv-divergence` | after the faults stop, every node's state machine is byte-for-byte identical |

A crash now also picks what the state machine keeps. A process kill keeps every
applied write, and a power loss keeps only what was flushed plus a random prefix of
the rest.

| ID | Command | Seeds | Pass criterion |
|---|---|---|---|
| S1 | `raftsim -first 1 -count 10000 -out results/sim.json` | 1 to 10,000 | 0 violations |
| S2 | `raftsim -first 2000001 -count 10000 -out results/audit/m3/sim-fresh.json` | 2,000,001 to 2,010,000 | 0 violations |
| S3 | `raftsim -first 3000001 -count 200 -lsm -out results/audit/m3/sim-lsm.json` | 3,000,001 to 3,000,200 | 0 violations, on the real LSM engine |

Development uses seeds from 900,000,000 up, so S1 to S3 stay unused until the final

## P. Planted bugs

The 9 Raft bugs from M2, rebuilt only where M3 moved the code they patch, must each
still fail `TestSimSchedules`. These new bugs must each fail the test named here:

| Patch | Rule it breaks | Test that must fail |
|---|---|---|
| `plain-leader-read` | a leader confirms its position before a read | `TestSimSchedules` |
| `read-skips-term-check` | a leader commits in its own term before reading | `TestReadWaitsForCommitInCurrentTerm` |
| `no-dedup` | sessions drop retried writes | `TestSimSchedules` |
| `sessions-not-in-snapshot` | a snapshot carries the session table | `TestSimSchedules` |
| `session-outside-batch` | a write and its session update are atomic | `TestSimSchedules` |
| `compact-without-flush` | the state machine is durable before the log is cut | `TestSimSchedules` |
| `install-keeps-conflicting-log` | Figure 13 step 7 discards a conflicting log | `TestSimSchedules` |
| `stale-snapshot-rolls-back` | an old snapshot can't move a node backwards | `TestSimSchedules` |
| `restore-position-lost` | a restored state machine records its position | `TestSimSchedules` |
| `save-before-restore` | the state machine is restored before the snapshot is recorded | `TestRestoreHappensBeforeSave` |

For each `TestSimSchedules` bug, `raftsim -first 1 -count 2000` also reports which
check fired, and how many seeds failed.

## C. Crash harness

The engine gains a new write path, so the harness reruns. This is
`crashtest -trials 500 -seed 1 -out results/crash.json`, with the same pass criterion
as H1 in `docs/acceptance/M0-fixes.md`.

## If something fails

The rule from `docs/acceptance/M2.md` applies: a failed criterion gets reported, a
real bug gets a regression test and an entry in `LEARNING.md`, and any code change
means S1 to S3 rerun on the final commit, on new seeds if S1 to S3 found the bug.
