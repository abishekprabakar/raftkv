# M4 acceptance criteria: a real network

Committed before any M4 code was written or run. The runner comes after the code it
runs, and is committed before it runs. `results/audit/m4/env.txt` records the commit
of each run.

## Scope

- **gRPC between nodes.** Raft messages are protobuf messages. Each node keeps one
  long-lived stream open to each peer and sends its one-way messages on it. Sending
  never blocks the Raft loop: each peer has a bounded queue, and a message that
  doesn't fit is dropped, which Raft already tolerates.
- **Fixed membership.** `--peers` lists every member, and it never changes. The
  tests run 3 and 5 nodes; Docker Compose runs 3.
- **A node process, `raftkvd`.** A real clock drives `Tick`. The Raft log goes to
  `FileStorage` and the store to the LSM engine, both on disk.
- **A client service.** Writes (put, append, delete), reads through ReadIndex, and a
  status call. A node that isn't the leader answers with the leader's ID and address.
- **A client library and a CLI, `raftkv`.** They follow those redirects, and retry a
  write under the same client ID and sequence number, so a retried write applies once.
- **Docker Compose.** Three nodes, one named volume each.

Timing in Docker: a tick every 10 ms, election timeouts drawn from 500 ms to 1 s, and
a heartbeat every 50 ms.

Out of scope: TLS and authentication, membership changes, performance numbers (M6),
and linearizability checking of real runs (M5). The CLI runs inside the Compose
network, because the leader addresses nodes hand out are the names Compose gives
them.

## T. Build and tests

| ID | Command | Pass criterion |
|---|---|---|
| T1 | `gofmt -l cmd internal` | prints nothing (generated code is formatted too) |
| T2 | `go vet ./...` | exit 0 |
| T3 | `go test -count=1 ./...` | exit 0 |
| T4 | `go test -race -count=1 ./...` | exit 0 |
| T5 | `go list -deps ./internal/raft/... ./internal/kv ./internal/storage/...` | no third-party packages: the core stays dependency-free |
| T6 | `go list -deps ./cmd/raftkvd ./cmd/raftkv` | third-party packages come only from `google.golang.org/grpc`, `google.golang.org/protobuf`, `google.golang.org/genproto/googleapis/rpc`, `golang.org/x/net`, `golang.org/x/sys` and `golang.org/x/text` |

If gRPC itself needs a module not on that list, it goes in an addendum here before
the acceptance run, with the reason. No consensus or storage library is allowed in
any case.

## G. Tests over real gRPC

These run inside T3 and T4, on 127.0.0.1 with real files.

| ID | Test | Pass criterion |
|---|---|---|
| G1 | `TestMessagesRoundTrip` | every Raft message type, with every field set, comes back identical after protobuf encoding. The test fails if a field is added to a message and not to the encoding |
| G2 | `TestClusterOverGRPC` | for 3 and for 5 nodes: a client given one node's address writes a key, for each node in turn, and every key reads back through every node |
| G3 | `TestClientFollowsRedirect` | a client given only a follower's address completes a write, and reports one redirect, to the leader |
| G4 | `TestWritesContinueAfterLeaderStops` | the leader is stopped. A write through a surviving node succeeds on a new leader, and the old leader restarts from its files and catches up |
| G5 | `TestRetriedWriteAppliesOnce` | an append sent twice over gRPC with the same client ID and sequence number appears once |

## D. Docker Compose

Run by `scripts/audit/m4/compose.sh`, starting from no raftkv containers or volumes.

| ID | What | Pass criterion |
|---|---|---|
| D1 | One command starts the cluster: `docker compose up -d --build --wait` | exits 0, and within 30 s all three nodes name the same leader in the same term |
| D2 | Any node works. For each node, `raftkv --addr node<i>:7000 put` with only that node's address | all three puts succeed, and the two that went to followers show a redirect to the leader. Then each of the three keys reads back correctly through each of the three nodes, 9 reads |
| D3 | Killing the leader. 5 rounds, each: find the leader, `docker compose kill` it (SIGKILL), then put a new key through one survivor's address only, with a 20 s client timeout | every round passes all four checks below |
| D4 | `docker compose down -v` | exits 0 |

A D3 round passes when:

1. the put succeeds;
2. the survivors name a leader other than the killed node, in a higher term;
3. every key written so far, in D2 and in every round, reads back through a survivor;
4. after `docker compose start` on the killed node, it has applied at least the new
   leader's commit index from just after the put, within 30 s.

Each round records the time from the kill to the put succeeding. That is not a
benchmark: M6 measures failover over at least 30 trials.

## If something fails

A failed criterion gets reported, not rerun until it passes. A real bug gets a
regression test and an entry in `LEARNING.md`, and any code change means everything
here runs again on the final commit.
