# M2 acceptance criteria: deterministic simulation

Committed before any simulator code was written or run. The runner comes after
the code it runs and is committed before it runs. `results/audit/m2/env.txt`
records the commit of each run.

## Scope

`internal/raft/sim` runs real `raft.Node`s on a simulated network with a virtual
clock. One seed decides everything about a schedule: the fault plan, every delay
and drop, and every timeout. There are no goroutines inside a schedule and no real
time, so any failure replays exactly from its seed.

The simulated network must do all of these:

| Fault | Meaning |
|---|---|
| Drop | a message is lost |
| Delay | a message arrives late, including long delays spanning several election timeouts |
| Duplicate | a message arrives more than once |
| Reorder | a later message on a link overtakes an earlier one |
| Partition | groups of nodes are cut off, including one-way cuts, and later heal |
| Crash-restart | a node dies and restarts from durable state: between events, during a `Save` so the update is lost, and after a `Save` but before its messages leave |

## Checks

Every schedule ends with a quiet phase: all faults stop and all nodes come back.

**Properties**, the guarantees Raft makes:

| Check | Meaning |
|---|---|
| `election-safety` | at most one leader per term, across the whole schedule |
| `log-matching` | two entries with the same index and term have identical entries before them, across the whole schedule |
| `leader-completeness` | a leader holds every entry committed in its term or earlier |
| `state-machine-safety` | no two nodes apply different entries at an index, including across restarts |
| `liveness` | in the quiet phase, a leader emerges and a new command reaches every node |

**Monitors**, which compare each step with the rules in Figure 2:

| Check | Meaning |
|---|---|
| `vote-once` | a node grants at most one candidate per term, across restarts |
| `durable-promise` | when a message leaves, the term, vote or entries it relies on are already on disk |
| `durable-apply` | an entry is on the node's disk when it is applied |
| `commit-majority` | when an index is first seen committed, a majority has it on disk |
| `commit-bound` | an accepted AppendEntries moves the commit index no further than receiver rule 5 allows |
| `commit-monotonic` | a running node's commit index never decreases |
| `term-monotonic` | a node's term never decreases, across restarts |
| `state-order` | `lastApplied <= commitIndex <= last log index`, and memory matches disk at each step |
| `panic` | a `Node` assertion fired |

### P. All 9 planted bugs must be caught at cluster level

The patches are the 9 from `scripts/audit/m1/`, unchanged. Each goes on a
throwaway copy, and these run on it:

| ID | Command | Pass criterion |
|---|---|---|
| P1 to P9 | `go test -count=1 -run TestSimSchedules ./internal/raft/sim` | fails for every one of the 9 bugs |
| Q1 to Q9 | `raftsim -first 1 -count 2000` | reports which check fired first, the first failing seed and how many seeds failed |
| R1 to R9 | `raftsim -first 1 -count 2000 -properties-only` | reports whether the five properties catch the bug with every monitor off |

R has no pass criterion, because it answers a different question: a monitor can
flag a broken rule that causes no visible harm. The predictions below are recorded
so that any surprise is visible. They are not pass criteria.

| Bug | Prediction |
|---|---|
| `send-before-save` | `durable-promise` in almost every schedule. With monitors off, a crash during `Save` is needed |
| `forget-voted-for` | `vote-once`. With monitors off, `election-safety` in a few schedules |
| `count-old-terms` | `leader-completeness`, rarely, in the Figure 8 profile. This one is at the most risk of not being caught |
| `always-truncate` | `panic` from the committed-entry assertion |
| `commit-to-last-index` | `commit-bound` only. Reasoning from the code, this bug may break no property here: a leader's `nextIndex` never drops below the point where a follower diverges, so any accepted message that reaches a stale tail removes it |
| `no-up-to-date-check` | `leader-completeness` |
| `commit-can-decrease` | `commit-monotonic` |
| `fixed-timeout` | `liveness`, in lockstep schedules with no crashes |
| `save-after-apply` | `durable-apply`. With monitors off, `state-machine-safety` in one-node schedules |

## Addendum: a real bug found in development

Written after development runs on seeds from 900,000,000 up, and committed before
any acceptance seed ran. The criteria above are unchanged.

The first development run reported no violations, but its counters looked wrong:
48,604,809 messages across 700 schedules, and 1,967,759 in one 5-node schedule that
should need a few thousand. `handleAppendEntriesReply` answered every reply that
left a follower behind with another send. Each such send starts a chain that lasts
until the follower catches up, and each heartbeat, proposal and duplicate started
another, so chains piled up behind any slow follower. That is a real bug in
`internal/raft`, with no safety impact. A leader now sends again only when a reply
taught it something new, and the heartbeat picks up after any lost reply.

| ID | Patch | Tests | Pass criterion |
|---|---|---|---|
| U1 | `unfix-message-storm` | `TestRepeatedReplySendsNothing`, `TestRepeatedRejectionSendsNothing`, and `TestNoMessageStorm` in `internal/raft/sim` | all three fail without the fix |

Two simulator problems also came up in development. Neither was a Raft bug:

- Seed 900,000,165 reported a liveness failure that was really my budget being too
  short: catching up about 1,500 entries, one per message, with delays still at
  chaos levels, took more than 30 virtual seconds. Delays now drop to 5 ms or less
  in the quiet phase, and liveness means no node applied anything for 5 seconds.
- A planted bug could leave a cluster applying forever with one node stuck, so a
  schedule never ended. The quiet phase now fails `liveness` after 60 seconds.

## If something fails

A failed criterion gets reported. If it is a real Raft bug, it gets a regression
test named after the failing seed and an entry in `LEARNING.md`, whether it shows
up in development or in acceptance. After any change to `internal/raft`, or to the
simulator, S1 and S2 rerun on the final commit. If S1 or S2 itself finds a bug, the
rerun uses new seeds as well, and the report says so.
