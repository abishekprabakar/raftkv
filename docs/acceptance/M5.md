# M5 acceptance criteria: partitions on real containers, checked with Porcupine

Committed before any M5 code was written or run, and before any partition code. The
runners come after the code they run, and are committed before they run.

## How reads are served right now

Read from the code at commit `e810010`, before any M5 change.

**ReadIndex. Not a local read on the leader, and not a lease.** A client's `Get`
goes `kvService.Get` → `kv.Server.Read` → `raft.Node.ReadIndex`, and the store is
read only in `kv.Server.ReadReady`. Nothing else in the server reads the store.

1. A node that isn't the leader refuses at once with `NotLeader`, naming the leader
   if it knows it.
2. A leader that hasn't yet committed an entry in its own term refuses with
   `ErrNotReady` (gRPC `Unavailable`).
3. Otherwise the leader notes its commit index, bumps its read sequence number and
   sends AppendEntries carrying it to every peer.
4. The read is served only once a majority, counting the leader, has answered with
   that sequence number or a later one, in the leader's current term, and the store
   has applied through the noted index.
5. A read not confirmed within 2 election timeouts fails with `ErrRetry` (gRPC
   `Unavailable`). In Docker that is 2 × 50 ticks × 10 ms = 1 s.

**Can a deposed leader return a stale value? Not through `Get`.** A leader cut off
from the majority gets no answers from it, so step 4 never completes, and the read
fails after 1 s. If its messages do reach a node in a newer term, the answer carries
that term and the old leader steps down, failing every pending read. The CLI retries
until its own timeout and then exits with an error, without printing a value.

**What is missing: check-quorum.** A leader never steps down on its own. Cut off, it
keeps believing it leads until it hears a higher term, so it keeps accepting writes
that can never commit. Those time out with their outcome unknown. That costs
availability, not correctness.

Prediction: the Docker stale-read test below passes on the current code. If it
fails, reads get fixed, with check-quorum added so a cut-off leader steps down, and
the test runs again.

## S. Scripted stale read on Docker

`scripts/audit/m5/stale-read.sh`, 5 rounds, each on a fresh cluster:

1. Start 3 nodes and write `x=1`.
2. Find the leader L, and `docker network disconnect` L from the Compose network.
3. Wait until the other two agree on a new leader in a higher term, and write `x=2`
   through it.
4. Check the trap is set: L still reports itself leader in its old term, and has
   applied the write of `x=1`.
5. Read `x` from L, with the CLI run inside L's container against `localhost:7000`
   only, and a 5 s timeout. `docker exec` doesn't need the network, so this reaches
   L however it's cut off.
6. Reconnect L. It must step down, and `x` must read back as 2 through every node.

| ID | Pass criterion |
|---|---|
| S1 | in all 5 rounds, the read from L is refused or redirected: the CLI exits non-zero and prints no value. Printing `1` is a failure, and so is printing anything else |
| S2 | in all 5 rounds, step 6 holds |
| S3 | on an image built with `scripts/audit/m3/plain-leader-read.patch`, the same script fails S1 in all 5 rounds, by printing `1` |

S3 shows the script can fail.

## C. Fault schedules checked with Porcupine

`cmd/chaos` runs one seeded schedule per seed, each on a fresh 3-node cluster:

- **Clients.** 6, two inside each node's container, run through `docker exec`.
  Each talks first to its own node at `localhost:7000`, so clients on a cut-off
  node keep talking to it, as Jepsen does. Each client does one operation at a
  time: get 40%, append 50%, put 10%, on 8 keys. Every appended value is unique, so
  a duplicate or lost append shows. Pauses between operations are 0 to 40 ms. An
  operation gets 4 s, and each attempt at one node 1 s.
- **Faults.** From 2 s to 18 s, partitions alternate with heals. Each partition
  lasts 2 to 6 s and each heal 1 to 3 s. A partition isolates the leader (50%), one
  follower (30%) or two nodes (20%), using `docker network disconnect`. At 20 s
  everything heals.
- **End.** Wait up to 20 s for all three nodes to name the same leader in the same
  term. Then every client reads every key once.
- **History.** The harness records each operation's call and return time on one
  clock, on the host. That is slightly wider than the real interval, which can hide
  a violation but never invent one. A write that fails or times out has an unknown
  outcome: it may have happened, so it is kept with no return time. A read that
  fails is dropped, because it observed nothing.

The seed fixes the faults, their timing, and every client's operations. It doesn't
fix how real processes interleave, so a rerun of a seed is a similar run, not the
same one.

| ID | Command | Seeds | Pass criterion |
|---|---|---|---|
| C1 | `chaos -first 1 -count 100 -out results/chaos.json` | 1 to 100 | Porcupine finds every history linearizable: 0 violations, and 0 checks that time out (120 s each) |
| C2 | the same run | | in every schedule, after the final heal, the three nodes agree on a leader within 20 s and every final read succeeds |

Development uses seeds from 900,000,000 up, so seeds 1 to 100 stay unused until the
final code commit.

### Failover time, read from logs

For each leader isolation: the time from Docker's `network disconnect` event for the
leader's container to the first line in any other node's log saying it became
leader in a higher term. Both clocks are the Docker VM's, so the two times are
comparable. Reported: count, median, 95th percentile and maximum, and the number of
isolations that ended with no new leader. This is a measurement with no pass
threshold. Logs and events for every schedule are kept in `results/audit/m5/`.

## Addendum: changes made in development

Written after development runs on seeds from 900,000,000 up, and committed before
seeds 1 to 100, or the acceptance rounds of the stale-read script, ran. One
development round of the stale-read script ran first, and passed.

**Two real liveness bugs.** Development runs found two bugs that left the cluster,
or a client, stuck long after the network healed. Neither broke linearizability:
Porcupine passed every development history. C2 would have caught both.

1. *Nodes kept dialing an address that belonged to another node.* When two nodes are
   cut off and reconnected, Docker can give each one the other's IP address; node2
   and node3 were seen swapping. gRPC's default resolver caches a name and looks it up
   again at most every 30 s, so node1's connection to "node2" reached node3. Node3
   refused every stream, because each envelope names its receiver, so nothing was
   misdelivered. But the connection was healthy, so gRPC kept reusing it, and the
   logs show a stream opened and refused on it every 50 ms while elections failed.
   Fix: dial with the `passthrough` scheme, which looks the name up on every
   connection attempt, and when a stream is refused as misaddressed, close the
   connection and dial again. Regression test: `TestPeerRedialsWhenItReachesTheWrongNode`,
   which fails without the fix.
2. *A client kept sending on a dead connection.* The client library had no keepalive,
   and a connection that died during a partition stayed open. Every attempt on it
   timed out, and in one run a client on node1 failed every operation from 7 s in
   until the run ended about 48 s later, including all its final reads. Fix: the client uses the same
   keepalive as the nodes, and an attempt that times out drops its connection.
   Regression test: `TestClientRedialsAfterATimeout`, which fails without the fix.

After both fixes, 20 development schedules (seeds 900,000,020 to 900,000,039) all
recovered and all their final reads succeeded.

**A wrong claim in M4.** M4's notes say peers ping every 2 s. gRPC silently raises
any client keepalive interval under 10 s to 10 s, so it was always 10 s. The code now
says 10 s, so behavior is unchanged. The 2 s timeout is real: on Linux, gRPC uses it
as `TCP_USER_TIMEOUT`. The M4 notes are corrected.

**Harness changes.**

- Docker's network events are recorded as they happen. Asking afterwards with
  `--since` lost most of them: Docker keeps a short backlog, and a run's many
  `docker exec` calls overflow it.
- Each node logs when a stream to a peer opens or is lost. That is how bug 1 was
  found.
- The history keeps each failed operation's error, and every run's logs, events
  and history are kept compressed.
- Not changed: a reconnected node's IP address isn't pinned. Containers get new
  addresses in real deployments too, so the system has to cope, and now it does.

With the planted `plain-leader-read` bug, 2 of 4 development schedules were found
not linearizable, so P2 is expected to pass.

## If something fails

A failed criterion gets reported, not rerun until it passes. A real bug gets a
regression test and an entry in `LEARNING.md`, and any code change means everything
here runs again on the final commit, on new seeds if these seeds found the bug.
